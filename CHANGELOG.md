# Changelog

Both plugins are for Invision Community 4.7. Newest first.

## Performance Optimizer

| Version | Date | Changes |
| --- | --- | --- |
| 1.19.0 | 2026-10-21 | "Send post" no longer waits for Elasticsearch. A new post, an edit, hiding, approving or deleting content changes the search index at once: IPS sends Elasticsearch up to six requests per change, fifteen for a post through the REST API, and the member waited for all of them (measured on a forum: 123 ms of a 297 ms reply on average and several seconds at the worst moments; 1.3 s of 1.8 s for a post from the mobile app). Under PHP-FPM the same changes are now made by IPS's own code, in the same order, right after the page has been sent. The post and its topic are loaded from the database again then, so a post deleted or hidden in the meantime is indexed as it is. On Elasticsearch 7.17 in a test: a reply 41–50 ms → 4–5 ms. A request that changes the same topic several times (a moderator hiding several posts at once) leaves the index IPS leaves when those changes come one by one; IPS alone could flag a post it had just hidden as the topic's last one. Also fixed: emails of tasks IPS runs while ending a request (1.6.0 kept them and they were never sent). Separate switch; needs Elasticsearch and PHP-FPM. |
| 1.18.0 | 2026-10-19 | Lifetime licence for every copy for now: the plugin no longer asks for a key and does not contact the licence server, IPS checks for new versions, and the settings show one line, "Lifetime licence". A key of the IQL Performance Suite (one key for both plugins) is accepted as well as a key of the Optimizer alone; before, a suite key was refused. |
| 1.17.0 | 2026-10-19 | A topic's first and last post now always the same post as IPS returns. Since 1.1.0 the plugin forced the topic's index (`FORCE INDEX(first_post)`) for IPS's "first or last post of a topic" query. When that post was written in the same second as the next one and IPS reads another index (`topic_id` with `queued=0`, where the author decides the tie) or sorts, the plugin returned the other of the two posts; for a member's last post in a large topic it was also slower than IPS's own plan. The plugin now only leaves out the date index of the whole forum (`IGNORE INDEX(post_date)`), as for topic pages since 1.13.0: IPS's own plan wherever the database would not use that index, the topic's index in the same order where it would. Tested on MariaDB 10.4 with every query of this shape IPS sends (about 25,000 checks per seed): the same post every time; where IPS walked the date index, 0.6–1.2 s → 1–2 ms. Needs the `post_date` index as well; the settings page says when it is missing. |
| 1.16.0 | 2026-10-19 | Topic pages in the REST API for moderators: when a moderator (the mobile app among others) reads a topic's posts through the REST API with hidden=1, MariaDB picked the date index of the whole forum for the first and the last pages of a large topic, as it did on the forum's own topic pages before 1.13.0 (97 ms on average in the Monitor's dump). The plugin now leaves out only that one index for exactly this query, so the database reads the topic's own index. On a test database: 0.1–1.9 s → 0.3–1.4 ms with 0.5 million posts, 2–14 s → 0.5 ms with 3.2 million. Every other page is planned exactly as by IPS and returns the same posts in the same order, posts written in the same second included. The API's usual query (hidden=0) stays as it is: the database already reads the topic's index there. Part of the "Pages of large topics" switch. |
| 1.15.0 | 2026-10-19 | Profile fields in the REST API: for every post, topic and Pages record in a response (the mobile app among others), IPS selected its author's profile field values with a query of its own, again and again for the same member. Measured over about 17 hours: 17.5 such queries per page of a topic's posts, 24.7 per list of topics, 35 per list of Pages records. Each member's values are now read once per request. IPS's own code still decides which fields the asking member may see; values written during the request are read again at once. On a test database, a list of 35 records by 6 authors: 27–28 → 6 queries. Separate switch in the settings. |
| 1.14.0 | 2026-10-18 | Profile fields next to posts: for every viewer who is not an administrator, IPS selected the list of profile fields once per post author on the page (the same rows every time), and where the values did not come with the post (archived topics) each author's values with a query of its own. Measured over about 17 hours: 114,543 and 50,815 such queries, about 9 ms per topic page. The list is now read once per request and the values of the page's authors with one query. IPS's own code still decides who sees which field and which columns it asks for; a profile edited during the request is read again at once. For a guest: a topic page 17 → 2 queries, an archived topic with 16 authors 50 → 20. |
| 1.13.0 | 2026-10-18 | Pages of large topics: for the first pages of a large topic (and the last ones, which IPS reads from the end) MariaDB picked the date index of the whole forum and walked hundreds of thousands of posts. The plugin now tells the database to leave out only that one index, so it reads the topic's own index. On a test database with 3.1 million posts: page 1 of topics with 12,000–110,000 posts 0.6–3.6 s → 0.5–0.7 ms, last pages up to 35 ms → 0.5 ms. Every other page is planned exactly as by IPS, and every page returns the same posts in the same order, posts written in the same second included. Separate switch in the settings. |
| 1.12.0 | 2026-10-18 | Fix for an IPS 4.7 bug with Elasticsearch: with "Maximum Results" below 1000, Elasticsearch refused some of IPS's index updates and deletes by query (they give no batch size, so it reads 1000 at a time), and IPS never checked. Older posts kept the last-post marker, so a topic showed up several times in unread content, and deleted content stayed in search. The plugin now gives those requests a batch size the index accepts; the index gets what IPS sends with 1000 or more. The settings page warns when the index's result window is below 1000. |
| 1.11.0 | 2026-10-18 | Licence key in the settings: saving activates it for the forum's domain, removing it detaches it. A background task checks it once a day, never during a page view. Without a valid licence every fix works the same; the ACP shows a message and IPS is not told about new versions. Answers of the licence server are signed (Ed25519); when it does not answer, the last known state stays. |
| 1.10.0 | 2026-10-17 | The settings page shows, for every fix, whether it works on this forum and why not (no Forums or Pages, clubs off, no Redis, datastore outside Redis, no `first_post` index, no postnotes, no PHP-FPM, templates not on disk). IPS checks for new versions on its own. |
| 1.9.0 | 2026-10-17 | Pages "Blocks" sidebar widgets are loaded with the page's other blocks: 5 fewer queries per topic page, 4 per Pages page. |
| 1.8.0 | 2026-10-16 | Pages blocks of a page in one query, with their categories one level per query. Topic page blocks: 52 → 18 ms. |
| 1.7.0 | 2026-10-15 | Template groups stored with an old theme cache key are compiled again instead of being rewritten on every request. Ends "Class … not found" errors after a cache clear. |
| 1.6.0 | 2026-10-15 | Notification emails are sent after the page has gone to the user. Application extension files are read once per request. |
| 1.5.0 | 2026-10-15 | A post author's clubs from memory and Redis. Topic pages without loading the whole forum tree. Post notes (postnotes add-on) checked once per topic. |
| 1.4.0 | 2026-10-14 | Theme tree and Pages database pages in one query. Language strings from Redis. |
| 1.3.0 | 2026-10-14 | Forum tree: one query per level instead of one per forum. |
| 1.2.0 | 2026-10-14 | The club of every club forum in one query. |
| 1.1.0 | 2026-10-14 | A topic's first and last post through the topic's own index: 4.018 → 0.001 s on a large forum. |
| 1.0.1 | 2026-10 | Language strings in REST API responses: 2.4–2.8 → 0.04–0.05 s on a large response. |
| 1.0.0 | 2026-10 | Language strings replaced in one pass, file URLs once per tag, recognize checked after the permission, datastore keys from Redis in one round trip. |
